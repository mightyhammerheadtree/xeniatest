# The Xenos GPU on WebGPU

The Xbox 360's Xenos GPU is the single biggest blocker between "recompiled homebrew" and "boots a title". This document tracks the port: what exists, what is honest about not working yet, and the order in which pieces come up. The architecture is xenia's — a register file driven by a PM4 command processor that emits draws against a unified shader core — re-hosted on WebGPU instead of D3D12/Vulkan.

xenia-canary (BSD-3-Clause) is the reference for every semantic decision in this directory. The relevant upstream files live in `gpu/` upstream: `command_processor.cc`, `register_file.cc/h`, `xenos.h` (register table + `GpuSwap32`), `pm4_command_processor_implement.h`, and the `shader_translator.*` family. Where this port deviates, it is called out in a comment next to the code.

## What works today (measured, not aspirational)

- **PM4 packet decode** for the full type-0/1/2/3 surface xenia implements on the CPU, including bit-exact `GpuSwap32` endianness handling (kNone/k8in16/k8in32/k16in32) for `MEM_WRITE` / `REG_TO_MEM` / index data.
- **Register file** with xenia's reset defaults and an ordered write log; reads of out-of-range indices throw instead of masking.
- **DRAW_INDX decode** exactly as xenia's `ExecutePacketType3Draw`: VGT_DRAW_INITIATOR (0x21FC) fields, `IsMajorModeExplicit`, kDMA index fetch (`VGT_DMA_BASE` 29-bit GPU bus mask, swap mode from `VGT_DMA_SIZE`) with immediate/auto-index/immediate-source handling; kImmediate traps (xenia does not support it either).
- **SET_CONSTANT** for ALU / fetch / bool / loop / REGISTERS constants, matching xenia's base addresses (ALU 0x4000, fetch 0x4800, bool 0x4900, loop 0x4908, context registers at 0x2000).
- **EVENT_WRITE / EVENT_WRITE_SHD**: initiator low 6 bits → `VGT_EVENT_INITIATOR`, `0x80000000` bit selects GPU-counter-write semantics (counter increments per event), the WRITEBACK_START/SIZE window (0x7F000000+off) translation for out-of-bus writeback addresses, and the 16/32/64-bit counter/payload sizes with GpuSwap endianness. `EVENT_WRITE_CFL/EXT/ZPD` are forwarded to the backend (`eventWrite`), not swallowed.
- **REG_RMW** including register-operand and_mask/or_mask bits (0x80000000/0x40000000), with the 13-bit register mask xenia applies.
- **WebGPU plumbing**: adapter/device request, canvas configuration, depth24plus-stencil8 texture, index-buffer upload with BE swap, **vertex-buffer upload with BE swap** (`uploadVertexBuffers()` — fetch constants → descriptors → VERTEX|COPY_DST buffers with GpuSwap endianness, uploaded per draw), present on `swap()`. The triangle placeholder exists so the pipeline can be visually verified once a browser is attached — it is *not* the guest shader and is only reachable with `{ placeholderShader: true }` passed explicitly.
- **Ring buffer + doorbell** (`ring_buffer.js`): `VdInitializeRingBuffer` zeroes the ring (like xenia) and seeds the read pointer; `VdEnableRingBufferRPtrWriteBack` records the writeback target; `updateWritePointer` (the CP_RB_WPTR doorbell) gathers `[read, write)` with wraparound and executes it through the command processor, traps when the guest is more than one ring ahead of the GPU (xenia reads garbage there; this build refuses), treats `0xBAADF00D` as "nothing to do", and performs the big-endian read-pointer writeback after every drain. End-to-end tests run a flat 64 MiB arena through the HLE Vd* exports → hook → ring → CP.
- **Vertex fetch decode** (`vertex_fetch.js`): the 96 vertex fetch constants (`xe_gpu_vertex_fetch_t`: type / 29-bit byte base address / endianness / size), a ucode walker replicating `AnalyzeUcode` (exec-family control flow pairs, sequence bits), and `VertexFetchInstruction` decode (stride in dwords, signed dword offset, format, dest-swizzle written mask) with the exact binding/attribute grouping xenia uses. `buildGpuVertexBufferDescriptors()` emits GPUVertexBufferLayout-shaped descriptors (arrayStride, offset, provisional shaderLocation = dest GPR). Formats WebGPU cannot represent trap instead of being silently reinterpreted — unorm/snorm 32-bit, 11-11-10 floats, signed 2-10-10-10, exp_adjust ≠ 0.
- **RB_* render-target decode** (`render_state.js`): the command processor snapshots the render-target registers at draw time (`colorInfo0..3`, `depthInfo`, `colorMask`, `blendRed..Alpha`, `stencilRefMask[Bf]`, `depthControl`, `blendControl0..3`, `colorControl` — raw values, like the ALU/bool constant snapshots) and the backend decodes them into pipeline state: `RB_COLOR_MASK` nibble 0 (normalized by format component count, xenia-style) → `writeMask`; `RB_BLENDCONTROL0` → blend state with xenia's enable rule (src=one/dest=zero/add on both equations disables; alpha slot reinterprets the color factors as xenia's `kBlendFactorAlphaMap`; unlisted 5-bit factor values map to `zero` like xenia's 32-entry tables); `RB_BLEND_RED/GREEN/BLUE/ALPHA` → `setBlendConstant` (IEEE-754 bitcast from the register file dwords); `RB_DEPTHCONTROL` → `depthCompare` (Xenos and WebGPU compare functions share the 3-bit numbering), `depthWriteEnabled`, and front/back stencil ops masked/mapped 1:1 from Xenos to WebGPU enum numbering, with the back-face fields used when `backface_enable` is set; one stencil reference per pass (the BF ref may not differ when back faces are in effect); `RB_COLOR_MASK`/`RB_BLENDCONTROL[1-3]` for RT1–3 decode but are ignored — MRT still traps at the translator. Decode is memoized per raw snapshot (bounded) — ~0 cost on repeated frames.
- **ucode → WGSL translator** (`wgsl_translate.js`, v1 subset, vertex + pixel): the Xenos microcode for ALU-only vertex shaders is decoded the way xenia does it (exec-family CF walker with live-shrinking CF bound, vfetch + ALU instructions, vector/scalar co-issue lanes) and emitted as WGSL. Vector ops compile to plain arithmetic with xenia's select-based `max`/`min` (not `fmax`/`fmin` — NaN bits matter for parity), `mad` → `fma`, `frc/trunc/floor`, `dp4/dp3/dp2add` expanded manually with a manual dot chain (xenia uses `NoContraction`), comparisons as `cmp` + `select`. Scalar ops maintain `ps` (previous scalar) including `*_prev` forms; `setp_*` ops write the single hardware predicate `p0` plus `ps`. Instruction-level predication emits `if (p0)`/`if (!p0)` blocks; `cexec`/`cexece`/`cexec_pred` CF emit `if (bc(n))`/`if (!bc(n))`/`if (p0)` blocks wrapping the predicated body (GPU bool constants bind as `array<u32, 8>`). Constants bind as `fc: array<vec4f, 256>`; bools only when used. Export lanes reconcile the dual-issue halves exactly like xenia: vector-only lanes take the vector value, scalar-only lanes take `ps`, both-halves lanes write literal `1.0`, and neither-half lanes with a scalar destination-relative address write `0.0`; untouched lanes keep the zero-initialized `out` member. Interpolators `@location(N)`, position `@builtin(position)`. Unsupported constructs trap loudly — loops, `cond_call`/`return`/`cond_jmp`, texture fetches, memory exports (32–37), kill-vertex export (63), vector dest GPR ≥ 30, attribute dest GPR ≥ 16 (WebGPU `maxVertexAttributes`), `+aL` register-relative addressing of any flavor, aL/const-addressed constants, cube/maxa/maxas (a0 writes), mulsc/addsc/subsc, SM-3 transcendentals, muls_prev2/pixel-kill scalars, and unassigned opcodes. Every generated shader that is expected to compile is compiled by **Dawn** (the real WebGPU compiler, null backend via the `webgpu` npm package) in `core/tests/test_wgsl_translate.mjs` — 101 tests, no mocks of the compiler. **Pixel shaders** decode with the same machinery: `oC0` color export (MRT `oC1–3` and `oDepth` trap with a named reason), interpolator inputs declared only at the lanes the vertex shader actually exports (`translateShaderProgram` computes the intersection — a fragment input without a matching vertex output is a pipeline-creation error, so unwritten lanes read as zeros, like xenia's zero-initialized GPRs), the kill ops (vector `kill_eq/gt/ge/ne` → `discard` on any lane, scalar `kills_*` → `discard` on the W lane vs `0.0`/`1.0`; vertex stages trap on kills as before), and the `oDepth` export → `@builtin(frag_depth)` with xenia's lane-X reconciliation and `[0,1]` clamp (dawn-verified to require depth-stencil state, which the pipeline now carries). Both stages are translated as one pair sharing the constant bindings (`fc` @0, `bools` @(usesFloat ? 1 : 0)) so the auto pipeline layout merges cleanly, and translated pairs are link-checked in tests with an actual null-backend pipeline. The translator is wired into `draw()` (see below) — translated shaders run on the default draw path.
- **The draw path executes the translated vertex shader** (`webgpu_backend.js#draw`, default mode — no opt-in): with a vertex shader loaded via `IM_LOAD`/`IM_LOAD_IMMEDIATE` (type 0), `draw()` translates the guest microcode of both stages (memoized per (vs, ps) ucode pair — never per draw), prepares the fetch plan (existing memoization), uploads buffers (content-addressed), snapshots and content-hashes the ALU (1024 dwords) and bool (8) constants from the register file into persistent `fc`/`bools` uniform buffers (re-uploaded only when a draw changed them), builds one pipeline + bind group per (shader pair, layout, topology) (cached, never per draw), and renders with the Xenos primitive type mapped to a WebGPU topology (point/line/triangle list/strip; fan/quad/polygon/rect trap loudly — connectivity would need index conversion). When no pixel shader is loaded the fragment stage is a **fixed, clearly-labelled bring-up FS** (constant amber — never guest state); when one is loaded the translated guest pixel shader runs, sharing the constant upload (one `fc`/`bools` write serves both stages). Every draw also snapshots the RB_* render-target registers and decodes them into the pass/pipeline (see the render-target bullet above); the pass always carries the canvas color attachment plus the depth/stencil attachment (cleared to 1.0/0). Honest failure modes, all loud: translation failure (with the translator's instruction-level diagnostic), a missing render-target snapshot (a host not attaching it refuses to draw), a guest ROP configuration WebGPU cannot represent (alpha test, GAMMA/float color formats, kD24FS8 depth, a back-face stencil reference different from the front face's), a translated VS reading attributes with no fetch constants in the packet, pure uint/sint attribute formats feeding the translated VS's `vec4f` inputs (WebGPU forbids it; fetch with the sign/normalize bit or as float), and any unsupported primitive topology. A vertex shader that fetches nothing draws correctly (geometry from constants only). `{ placeholderShader: true }` remains as the explicit bring-up tool (fetch placeholder pipeline / full-canvas triangle) — it is never used implicitly.
- **GPU buffer uploads are content-addressed** (`webgpu_backend.js`): vertex and index buffers are hashed (FNV-1a over the padded BE bytes) and cached by `(kind, base, size, endian)` — unchanged buffers at the same guest address are never re-uploaded or rebuilt per frame (a stale buffer at the same key is replaced when the content hash changes). Bounded by count (32 entries) and total bytes (128 MiB); LRU eviction destroys the evicted `GPUBuffer`. The ring drain reads contiguous runs with one `readGuestMemory()` call per run (≤2 per drain; a short-view implementation falls back to per-dword reads). The register-file write log is opt-in (`enableWriteLog()`) so the normal `write()` path allocates nothing. The fetch plan (ucode analysis + constant decode) is memoized per shader on a hash of the 192 fetch constants, and the fetch placeholder pipeline is memoized per plan (no per-draw JSON.stringify). Numbers from `tools/bench_gpu_hot_paths.mjs` (16K-dword ring drain): 11.1 ms → 3.1 ms; 2000 static fetch-draws: 70 ms → 12.8 ms (5.5×), 4000 buffer creations → 2.
- **GPU MMIO aperture** (`recompiler.js`, `gpu_host.js`, bring-up step 4.5): guest `stw`/`lwz`/`stfd`/`lfd` to `[0x00F02000, 0x00F03000)` (integer + FP load/store paths) reach the GPU host; CP_RB_WPTR (0x01C5) drains the command ring, CP_RB_RPTR (0x01C4) reads back the read pointer; other registers trap loudly. Recompiler integer + FP load/store paths emit the aperture branch next to the console MMIO branch.
- **Vertex fetch on the draw path** (WebGPU backend, behind the explicit `{ placeholderShader: true }` opt-in): the command processor snapshots the 192 fetch-constant dwords into every draw packet; `draw()` with a loaded vertex shader runs `prepareVertexFetch()` (decode constants → analyze → descriptors), uploads the buffers with `GpuSwap32` endianness, emits a fetch placeholder pipeline whose declared vertex-buffer layout and WGSL `vs_main` match the descriptors (attribute 0 → pass-through position, `enable f16` when an attribute needs it), binds the buffers with `setVertexBuffer`, and honors `isIndexed` (index buffer upload + `drawIndexed`). A VS that fetches nothing falls back to the full-canvas triangle (logged). This is bring-up plumbing, not translation: the placeholder VS is generated, the guest microcode is not executed yet.
- **Loud failure everywhere else.** Unknown opcodes, unsupported addressing modes, draws before `attach()`: all throw `XenosGpuError`/`XenosWebGpuError` with the packet/PC/register named. Nothing is silently miscompiled — same discipline as the PPC recompiler.

## What does not work yet (the honest list)

1. **Guest shader translation — still partial.** ALU-only vertex AND pixel shaders translate to Dawn-validated WGSL (see above). Still missing: texture fetches (`tfetch`) in any stage, loops/calls/jumps, register-relative (`+aL`) addressing, SM-3 transcendentals. The translator intentionally traps instead of miscompiling any of these.
2. **MRT render targets and formats beyond 8-bit unorm do not exist yet.** `oC1–3` exports trap loudly at the translator (the WebGPU pipelines bind only the canvas attachment); color formats other than `k_8_8_8_8` trap loudly when the pixel shader writes RT0 (gamma — because the PWL encode does not exist yet — and 10/16/32-bit unorm/float/snorm); kD24FS8 float depth traps when depth/stencil is active or `oDepth` is exported; alpha test traps (no WGSL representation, and the wrong comparison is worse than none); a back-face stencil reference differing from the front face's traps (WebGPU has one reference per pass). What is honored exactly: `RB_COLOR_MASK` RT0 writes, `RB_BLENDCONTROL0` blend + constants, depth test/write/compare, and stencil front/back state on the `depth24plus-stencil8` attachment. Also deliberate: draws with no vertex shader loaded refuse to render (no geometry to fabricate), unless you pass `{ placeholderShader: true }` for the bring-up triangle.
3. **Render targets are the canvas only — tiling, clears, scissor, and MSAA do not exist yet.** Guest render targets live in EDRAM; ownership/copy-back, `RB_COLOR_CLEAR`/`RB_DEPTH_INFO` clears, `SCISSOR` rects, and multisample resolve are all EDRAM render-target-cache work (see step 7). What the canvas target honors is listed under item 2.
4. **Shader bool/loop constants.** `FETCH_*` constants are now consumed (fetch path above); `BOOL_*`/`LOOP_*` remain decoded into the register file but no fetcher.
5. **GPU MMIO aperture (done — see step 4.5).** The flat 64 MiB arena cannot hold the real GPU BAR (0x7FC8_xxxx + register×4), so the recompiler routes a second window, `[0x00F02000, 0x00F03000)`, to the GPU host (byte offset = register × 4, same homebrew convention as the console MMIO at 0x00F00000). Only CP_RB_WPTR (0x01C5, the doorbell) is modeled on writes and CP_RB_RPTR (0x01C4) on reads; every other register traps loudly. A retail guest's real BAR accesses would need remapping onto the aperture (HLE) — that's the same convention the console MMIO uses.
6. **Vertex fetch is wired for both paths.** Buffers are uploaded and bound per draw (fetch constants change per draw in real games, so the plan is memoized per snapshot and uploads are content-addressed). The translated vertex shader declares `vec4f` inputs at `@location(N)` with N = dest GPR — matching `shaderLocation = dest GPR` — but pure uint/sint attribute formats cannot feed a `vec4<f32>` location (WebGPU interface matching), so draws with those trap loudly; fetch them normalized (unorm/snorm) or as floats instead.
7. **Textures, samplers, query (VIZ_QUERY), predication side effects** beyond register tracking.
8. **Browser-only.** Everything above runs in a real browser; node is used only for the PM4/CP/backend-honesty tests (no `navigator.gpu`). There is no headless WebGPU in CI yet.

## Bring-up order

1. ✅ Register file + PM4 decode with xenia-verified semantics (`core/tests/test_gpu_pm4.mjs`).
2. ✅ WebGPU device/canvas/depth/index-upload plumbing (`webgpu_backend.js`), placeholder triangle behind explicit opt-in.
3. ✅ Ring buffer: host-side ring with doorbell semantics, HLE Vd* exports, end-to-end tests (`ring_buffer.js`, `gpu_host.js`, `core/tests/test_gpu_ring.mjs`).
4. ✅ Vertex fetch decode: `FETCH_*` constants, ucode walker, `GPUVertexFormat` mapping, `GPUVertexBufferLayout` descriptors (`vertex_fetch.js`, `core/tests/test_vertex_fetch.mjs`).
4.5 ✅ GPU MMIO aperture in the recompiler: `[0x00F02000, 0x00F03000)` routed as `xenorecomp.gpu_mmio_store/gpu_mmio_load` (integer + FP load/store paths), forwarded by `makeImports` / export templates to `globalThis.XenonGpuHost.mmioStore/mmioLoad` (`gpu_host.js`); CP_RB_WPTR drains the ring synchronously (guest → recompiled store → aperture → doorbell → CP → memory, end-to-end tested), CP_RB_RPTR reads back the drained read pointer; every other register traps with its name. End-to-end test: a guest assembles a PM4 MEM_WRITE packet in ring memory, rings the doorbell via MMIO, and the bytes are in guest memory afterwards.
5. ✅ Shader HIR + WGSL codegen for ALU-only vertex shaders — translator done (vfetch → position/interpolator exports; `wgsl_translate.js`, 103 Dawn-validated tests, plus VS+PS pairs link-checked with an actual null-backend pipeline) **and wired into `draw()`**: the default draw path translates and runs both stages (pipeline/bind group per shader pair+layout+topology, shared content-hashed constants). The guest pixel shader runs when loaded — linked interpolators, merged constant bindings, kills → `discard`.
6. ◐ Pixel-shader render targets — **partially done.** Honor `RB_COLOR_MASK` RT0 writes, `RB_BLENDCONTROL0` blend (+ IEEE-754 blend constants), `RB_DEPTHCONTROL` depth/stencil on a `depth24plus-stencil8` attachment, and the `oDepth` export (`@builtin(frag_depth)`, clamped). Loudly traps: `oC1–3` MRT, color formats other than `k_8_8_8_8`, kD24FS8 depth, alpha test, BF stencil-ref mismatch.
7. ⬜ The EDRAM render-target cache: guest-memory color/depth targets, tiling-mode handling, `RB_COLOR_CLEAR`/clears, scissor, MSAA, gamma (PWL) encode, MRT, kD24FS8 depth — the real "render targets" step; the canvas-as-RT above is the bring-up subset.
8. ⬜ Textures + samplers (`VTXFETCH`, `SET_SAMPLER`), addressing modes.
9. ⬜ Queries (VIZ_QUERY), predication, EVENT_WRITE consumers (e.g. XMA fences).
10. ⬜ Boot a real homebrew title end-to-end; performance pass (index-buffer reuse, pipeline cache).

Each step lands as its own commit with tests; `npm test` must stay green.

## Testing

```
npm run test:gpu     # the gpu suite: pm4, webgpu, ring, vertex_fetch, vertex_binding, mmio, buffers, wgsl_translate, translated_draw, render_state
```

- `test_gpu_pm4.mjs` assembles real big-endian PM4 streams and executes them through the same modules the browser loads. It covers packet round-trips, constant windows, endianness rules, EVENT_WRITE counter/writeback mapping, DRAW_INDX decode, and predication.
- `test_gpu_webgpu.mjs` covers what can run without a GPU: constructor validation, the `attach()` error path in node, `memWrite` routing into guest memory, and loud traps (draw before attach). It does not mock a device.
- `test_render_state.mjs` covers the RB_* render-target decode: xenia's blend factor/op tables (color and alpha slots), the write-mask normalization, the depth/stencil field mapping (numbering shared with WebGPU), the memoized decode, and every named trap (alpha test, GAMMA/unsupported color formats, kD24FS8, BF stencil-ref mismatch, missing snapshot).
- `test_gpu_translated_draw.mjs` covers the draw path behind a recording fake device: translated modules, pipeline/bind-group caching (now keyed on the render-target state too), constant content-hash uploads, the RB_* snapshot → pass/pipeline state (write mask, blend factors/constants, depth compare/write, stencil front/back + reference), and the named traps.
- `test_gpu_ring.mjs` covers the ring: zero-on-initialize, doorbell execution through the real CP, wraparound, one-ring-overrun trap, `0xBAADF00D` sentinel, BE read-pointer writeback, and the HLE Vd* exports driven against a recording host (and the loud trap when no GPU host is attached). A final end-to-end test creates `XenonGpuHost` over a `WebAssembly.Memory`, drives the Vd* exports through the HLE, kicks the doorbell and observes the CP register file and the writeback.
- `test_gpu_mmio.mjs` covers the aperture: recording-host tests for store/load routing and the no-host loud trap, a real-`XenonGpuHost` end-to-end test (guest assembles a PM4 MEM_WRITE packet into ring memory, rings CP_RB_WPTR via MMIO, the bytes land in guest memory and the read pointer drains), and the FP store path.
- `test_gpu_vertex_binding.mjs` covers the vertex-binding draw path without a GPU: a recording fake device stands in for `navigator.gpu` (buffer creation/upload/swap, placeholder pipeline layout, `setVertexBuffer`/`drawIndexed` pass state), loud traps for non-vertex fetch constants, zero-size buffers, unrepresentable formats, stride-0; plus an end-to-end CP test asserting the 192 fetch constants reach the draw packet.
- `test_vertex_fetch.mjs` covers fetch constant decode, the ucode walker (bindings, written-mask filtering, vfetch_mini stride inheritance, loud traps on orphans/overflow), the `GPUVertexFormat` mapping table (including the formats that trap) and descriptor validation (stride overflow, negative offsets, shaderLocation collision).
- Anything touching an actual device (placeholder triangle, canvas present) is verified manually in Chrome/Edge until a headless WebGPU implementation is available; that checklist is this document, updated as bring-up advances.

## Updating the register table

`xenos_registers.js` is generated from xenia's `register_table.inc`:

```
node tools/gen_gpu_registers.mjs            # reads .xenia-ref/gpu/register_table.inc if present
node tools/gen_gpu_registers.mjs path/to/register_table.inc
```

`.xenia-ref/` is git-ignored (reference-only). Do not hand-edit the generated file; regenerate it and commit the diff.
